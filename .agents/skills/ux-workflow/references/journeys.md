# Journeys and structure

Apply to each affected task; record not applicable only with a reason. Prefer observed user needs over assumptions.

## Navigation and orientation
- Identify where users enter, move between related tasks, return, and resume. Ensure page titles, navigation labels, current location, and link destinations agree.
- Use persistent navigation for recurring, non-linear work when it helps; a linear process may need only clear forward and back paths. Do not add navigation levels without a task reason.
- Make specific records reachable from the list, notifications, or work queue that refers to them; preserve context on return where practical.

## Information architecture and hierarchy
- Group by user task and meaning, not storage model. Put information needed to decide beside the action. Keep essential status visible and distinguish similar records by meaningful context.
- Establish one clear primary task per view; make secondary actions discoverable without competing equally. Place destructive or infrequent actions away from routine actions and explain consequences.
- Compare list/detail, direct editing, and dedicated pages according to amount of work, need to compare, navigability, and interruption. Avoid repeating full forms for every row.

## Density, layout, and content
- Reveal optional complexity only when useful. Tabs suit clearly labeled related sections when users do not need to view all at once; they are poor for sequential forms or side-by-side comparison. Disclosures should not hide information all users need.
- Check scanning, alignment, spacing, text hierarchy, grouping, and reading order at desktop and narrow sizes. Support long names, translated text, zoom, and realistic data volumes.
- Use familiar, consistent terms and action-specific labels. Show dates, amounts, ownership, and statuses with enough context to interpret them. Explain prerequisites at the point of need.
